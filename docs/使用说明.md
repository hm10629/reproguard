# 使用说明

## 1. 安装

在项目目录执行：

```powershell
cd path\to\reproguard
python -m pip install -r requirements.txt
```

`pypdf` 只用于读取 PDF。若暂时无法安装依赖，TXT 和 Markdown 输入仍然可以运行。

## 2. 从论文或实验协议创建复现档案

该流程不要求代码仓库。默认手工模式先生成合法档案骨架，研究者随后补充主张、步骤、过程和证据：

```powershell
python -m src.protocol_extract `
  --paper data\examples\incomplete-ml-project\paper.txt `
  --output reports\reproduction-passport
```

输出：

```text
reports\reproduction-passport.json
reports\reproduction-passport.md
```

启用本地开源模型抽取：

```powershell
python -m src.protocol_extract `
  --paper D:\path\paper.pdf `
  --output reports\reproduction-passport `
  --model-mode ollama `
  --model-name qwen2.5:3b `
  --ollama-url http://127.0.0.1:11434
```

模型只能引用程序提供的 `P###` 来源编号。模型生成的研究主张、复现步骤和证据默认都是 `needs_review`，并自动生成待人工复核记录。

使用 DeepSeek 云端 API：

```powershell
$env:DEEPSEEK_API_KEY="你的密钥"
python -m src.protocol_extract `
  --paper D:\path\paper.pdf `
  --output reports\reproduction-passport `
  --model-mode deepseek `
  --model-name deepseek-chat `
  --api-base-url https://api.deepseek.com
```

程序只保存环境变量名，不保存或输出密钥。`【必须人工决定】` 使用云端模式前，确认论文、实验记录和其他科研材料允许发送给所选服务，并核对服务条款与数据保留政策。

校验已有档案：

```powershell
python -m src.passport `
  --input data\examples\reproduction-passport-demo.json
```

`data\schemas\reproduction-passport.schema.json` 是可复用的开放数据结构。Python 校验器还会额外检查 JSON Schema 难以表达的跨对象引用，例如步骤引用的证据是否真实存在。

## 3. 命令行体检（已有工具）

```powershell
python -m src.cli `
  --paper data\examples\incomplete-ml-project\paper.txt `
  --repo data\examples\incomplete-ml-project\repository `
  --output reports\demo-report
```

默认生成：

```text
reports\demo-report.json
reports\demo-report.md
```

只生成一种格式：

```powershell
python -m src.cli `
  --paper D:\path\paper.pdf `
  --repo D:\path\repository `
  --output reports\paper-report `
  --format markdown
```

## 4. 网页界面

启动本地网页：

```powershell
python -m src.web --host 127.0.0.1 --port 8765
```

打开：

```text
http://127.0.0.1:8765
```

网页工作台包含两个入口：

- “从论文或实验协议建档”只需要论文/协议路径，不要求代码；
- “论文 + 代码体检”保留原有15条规则检查。

创建复现档案后，可以进入“编辑步骤”补充手工步骤，再进入“记录实际过程”填写：

- 每个步骤的实际状态、参数和过程备注；
- 实验记录、日志或结果文件的位置与内容摘录；
- 本次运行环境、时间和主要结果。

网页保存后，JSON 与 Markdown 下载会包含实际过程和结果。研究者填写的证据使用 `user_supplied`，状态仍为 `needs_review`；这表示“已记录但尚未由复核者确认”。

记录完成后点击“检查最新运行偏差”，系统会确定性检查：

- 预期参数是否在实际记录中缺失；
- 预期参数与实际参数是否明确不一致；
- 标记为完成的步骤是否缺少实际过程证据；
- 整次运行已完成时，是否仍有未完成步骤。

自动发现的每条偏差都会创建待复核任务。复核者必须署名，可以接受、驳回或修订；驳回和修订必须填写理由。只有人工提交后，复核记录才从 `pending` 变为已处理。

`【必须人工复核】` 实际过程是否真实发生、参数是否准确、证据位置是否可以回查、结果值与单位是否正确。

网页读取本机路径，不连接 GitHub。手工、规则和 Ollama 模式不上传文件；只有用户主动选择 DeepSeek 云端模式时，来源文本才会发送到所配置 API。未安装或未启动 Ollama 时，可以使用手工建档和规则体检。

## 5. 运行测试

项目使用 Python 标准库测试：

```powershell
python -m unittest discover -s tests -v
```

测试总数以当前实际输出为准。其中 `test_load_pdf_when_pypdf_is_available` 依赖可选的 `pypdf`：

- 已安装 `pypdf`：输出 `Ran N tests` 与 `OK`
- 未安装：输出 `Ran N tests` 与 `OK (skipped=1)`，该项被跳过

两种结果都算通过，差异只反映依赖是否安装。本项目验证环境已安装 pypdf；使用者应先运行 `python --version` 和 `python -m pip show pypdf`，确认命令指向预期环境。

测试覆盖：

- TXT 和 PDF 论文读取
- 中文路径和本地目录扫描
- 忽略输出目录和超大文件
- 15 条规则的状态判断
- JSON/Markdown 报告
- 结构化待修复任务清单（字段、排序、排除项、空态）
- CLI 端到端调用
- 网页接口与任务展示、HTML 转义
- 复现档案结构、跨对象引用与人工复核约束
- 论文/协议来源编号和模型输出白名单
- 无代码建档及复现档案下载
- 手工步骤、实际过程、参数证据和结果记录
- 确定性参数对齐、缺失证据检测与署名人工复核
- DeepSeek/OpenAI 兼容请求格式、密钥隔离与来源白名单

## 6. 体检报告解释

`missing` 的含义是：

> 在当前检查范围内未找到相关信息。

这不等于证明项目绝对没有该信息。报告中的证据会指向论文页码、仓库文件和行号，方便人工确认。

### 6.1 待修复任务清单

报告中的「待修复任务」章节由未确认的检查项自动生成。只有状态为 `missing`、`partial` 或 `needs_review` 的项会进入清单，已确认（`found`）和不适用（`not_applicable`）的项不会出现。清单按高、中、低风险排序，同风险内按规则编号排序。

网页版在同一位置展示同样的清单，并在统计区给出「待修复」计数。

### 6.2 读这个章节时注意三点

**一、任务编号不是规则编号。** 每条任务标题上有两个编号：

- `T01` 是**任务编号**，表示它在本份报告中的顺序，换一份报告就可能变化
- `R002` 是**规则编号**，表示它对应哪条检查规则，是固定的

讨论修复顺序时用任务编号，跨报告引用问题时用规则编号。

**二、任务条数不等于检查条数。** 每次体检都执行全部 15 条规则。网页统计显示「检查项 15、待修复 10」，意思是另外 5 项已确认通过、无需处理，而不是只检查了 10 项。

**三、有没有证据位置，代表两类工作量完全不同的任务：**

| 报告显示的状态 | 内部状态 | 证据位置 | 需要做什么 |
| --- | --- | --- | --- |
| 部分满足 | `partial` | 有，指向具体文件和行号 | 线索已存在但不完整，补全即可 |
| 当前范围内未找到 | `missing` | 无，显示“当前检查范围内未找到” | 当前范围内没有该信息，需要从零建立 |
| 需要人工确认 | `needs_review` | 按设计为空（无法建立可靠对应关系） | 自动判断不可靠，需要人工判断 |

**关于「需要人工确认」的空证据。** 该状态不给出证据位置是预期结果，不是漏采证据。当论文中的模型、数据集或代码名称无法可靠对应到仓库内容时，程序不会把无关的文件或行号填进证据位置，以免污染证据本身的含义——每条证据都必须真的指向所声称的内容。这一类任务需要的是人工比对论文与仓库的对应关系，因此报告只能指出“这里需要人看”，给不出具体位置。

建议先处理有证据位置的「部分满足」任务：线索已经找到，投入小、收益明确。没有证据位置的任务通常需要补充新材料，工作量更大。

## 7. 本地模型模式（可选）

默认的规则模式完全离线，不需要任何模型。如果本机装有 Ollama 和任意的开放模型，可以额外让模型做实验要素抽取和人工复核提示。本模式不引入新的 Python 依赖。

先安装并启动模型：

```powershell
ollama pull qwen2.5:3b
ollama run qwen2.5:3b
```

命令行启用：

```powershell
python -m src.cli `
  --paper data\examples\incomplete-ml-project\paper.txt `
  --repo data\examples\incomplete-ml-project\repository `
  --output reports\demo-report `
  --model-mode ollama --model-name qwen2.5:3b --ollama-url http://127.0.0.1:11434
```

网页界面在表单里把「检查模式」选为「本地开源模型辅助」即可，模型名和地址可以留空使用默认值。

边界：

- 模型结果只出现在报告的「模型辅助结果」区块，标注为「不替代规则判定」，不会改写任何一条检查结论。
- 模型只能引用工具给出的来源编号（论文行 `P###`、仓库行 `F###`）；引用了清单外的编号，该条会被忽略。
- 不安装模型、或模型服务未启动时，报告会标注「模型不可用」并给出提示，规则结果照常输出。
- 论文和代码只在本机进程内处理，不上传，也不需要任何 API Key。

故障排查：

| 现象 | 处理 |
| --- | --- |
| 报告显示「模型不可用」 | 确认 Ollama 已启动，`ollama list` 能看到模型 |
| 提示连接被拒绝 | 检查 `--ollama-url` 是否指向真实的 Ollama 服务地址 |
| 模型返回内容不可解析 | 换用支持 JSON 输出的模型，或改用规则模式 |

## 8. DeepSeek / OpenAI 兼容模式（可选）

该模式与 Ollama 共用同一套提示协议、来源编号白名单、结构校验和人工复核流程。当前默认值为：

- API 地址：`https://api.deepseek.com`
- 模型：`deepseek-chat`
- 密钥环境变量：`DEEPSEEK_API_KEY`

也可以通过 `--api-base-url`、`--model-name` 和 `--api-key-env` 指向其他兼容服务。密钥缺失或服务不可用时，系统不会中断建档，而是生成待人工补充的档案骨架。

`【必须人工复核】` 模型版本、供应商条款、数据保留政策、输出内容和来源引用。云端模型输出仍是待复核建议，不是已确认科研事实。
