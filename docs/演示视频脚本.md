# ReproGuard 3—5分钟演示视频脚本

建议成片约4分20秒。录屏前关闭通知，隐藏本机用户名、密钥和无关标签页。所有线上画面必须来自实际运行。

## 0:00—0:25 开场与问题

画面：作品标题 + 一个科研PR diff。

旁白：

> 论文代码会持续变化。一次看似正常的Pull Request，可能修改批大小、验证样本范围或评价指标。普通代码审查能发现实现问题，却很难回答：这次变化是否改变了论文的复现条件？我们开发了ReproGuard复现守门人，把论文和实验协议中的约束带进GitHub PR。

## 0:25—0:55 工作流程

画面：简洁流程图。

旁白：

> ReproGuard读取PR差异和可选的论文、协议或复现档案。确定性规则识别参数、随机性、依赖、数据和评价流程变化；开源模型补充非结构化科研语义。每条输出都绑定代码行号或论文位置，最终由维护者确认，而不是由AI自动裁决科研正确性。

## 0:55—2:15 真实PR回放

画面A：浏览器打开Pytorch-UNet PR #141，显示已合并状态、URL和关键diff。

画面B：运行本地回放命令或显示GitHub Action运行结果。

画面C：打开`reports/pytorch-unet-pr-141.md`。

旁白：

> 这是2020年真实合并的Pytorch-UNet PR #141，完整diff哈希已经固定。ReproGuard目前给出三项高风险人工复核点。第一，评价结果使用数据加载器批次数进行归一化；第二，Sigmoid、Dice和交叉熵相关流程变化；第三，验证加载器新增`drop_last=True`，会改变参与验证的样本范围。系统不说这个修复是错误的，而是要求维护者核对论文、测试和结果是否同步。

操作：依次放大三条报告的行号和证据，不要快速滚动。

## 2:15—2:55 失败与改进

画面：评测报告中的“改进前后对照”表。

旁白：

> 我们没有只展示成功案例。对U-Net公开项目进行六条核心规则人工标注时，初始系统只与人工一致三条。漏报的共同原因是：文档提到了相关内容，但复现信息并不完整。我们把README安装与运行命令、数据获取语境以及代码和数据许可拆开检查，同组复测达到六条一致。由于样本很小、全部为正类，我们不会把它宣传成整体准确率百分之百。

## 2:55—3:30 AI与可解释性

画面：真实模型调用输出，显示模型名称、`D###`/`P###`引用和`needs_review`。

旁白：

> 模型只负责规则难以枚举的科研语义，并且只能引用系统提供的来源编号。无效引用会被丢弃，模型不能改写规则结论。即使模型服务不可用，离线规则仍可正常运行。

画面应使用`reports/ai-real-call.json`或Markdown结果：展示模型参数`deepseek-chat`、抽取状态`ok`、`P004`/`P005`等有效来源、`needs_review`，并展示沈智和签署的复核记录。说明保存的是处理后档案而非原始HTTP响应。

## 3:30—4:00 一键启用与开放成果

画面：当前公开GitHub仓库、`action.yml`、验收PR #1和成功Action运行；若录制前已发布`v1`，再补充跨仓库调用画面。

旁白：

> 项目已形成GitHub复合Action。PR #1已完成同仓库在线验收，warning、Job Summary、单条评论更新和报告artifact均已通过；当前仓库已经公开，但其他仓库通过`hm10629/reproguard@v1`接入仍需等待`v1`发布和跨仓库验证。我们已开放规则引擎、复现档案Schema、评测脚本、真实案例和合规文档。第三方论文、代码快照、数据和密钥不会被重新分发。

`【录制前核对】`仓库已公开，同仓库在线运行已经完成；`v1`和跨仓库调用尚未完成，旁白中不得说成已经支持`@v1`跨仓库调用。

## 4:00—4:20 结尾

画面：项目名称 + 一句话价值。

旁白：

> ReproGuard不替代科研人员，而是让关键变化更早被看见、每个判断都能追溯、每次复现都能留下开放证据。
