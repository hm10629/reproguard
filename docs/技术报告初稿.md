# ReproGuard复现守门人技术报告（初稿）

> 面向第八届全球校园人工智能算法精英大赛“AI+开源”主题赛。建议排版后正文控制在15页以内。所有标记为`【必须人工补充】`的内容不得由工具猜测。

## 摘要

开放论文代码不断通过Pull Request演进，但通用代码审查、安全扫描和依赖告警并不专门回答一个科研问题：代码变更后，论文或实验协议中的关键复现条件是否仍然成立？ReproGuard提出一种面向开放科研仓库的复现变更审查流程。系统解析PR统一差异，将实验参数、随机性、依赖环境、数据处理和评价流程变化与论文、协议或复现档案中的约束对应，输出带diff行号、来源位置、建议和人工复核状态的结构化风险。系统采用“确定性规则为权威、开源模型为受限辅助”的双层设计；模型只能引用系统提供的来源编号，未知引用会被丢弃，且模型不能覆盖规则结论。项目已形成GitHub复合Action、命令行与网页原型、开放Schema、评测脚本和152项自动化测试。真实PyTorch-UNet PR #141回放目前报告3项高风险复核点；U-Net第三方实现的6条核心规则评测记录了基线3/6一致、规则修复后同组6/6的过程及局限。

关键词：科研复现；GitHub Pull Request；开源协作；智能代码审查；证据链；人机协同

## 1. 问题与场景价值

### 1.1 真实问题

论文代码仓库并非发表后保持不变。维护者会修改训练参数、数据加载器、损失函数、评价指标、依赖版本和实验入口。普通代码审查可以讨论实现质量，Dependabot可以报告脆弱依赖，CodeQL可以寻找安全漏洞，但这些工具不以论文复现约束为核心对象。

典型风险包括：

- 批大小、学习率或随机种子变化，但论文与结果表未同步；
- 数据加载器开始丢弃尾批，验证样本范围发生变化；
- 指标的归一化分母从样本数改为批次数；
- 数据集名称存在，但下载、目录结构和预处理流程不完整；
- 代码许可证明确，数据或外部权重的使用限制却未披露。

这些变化不一定是错误，却应在合并前被明确提出并交由研究者确认。否则后续复现者只能从分散的代码历史中猜测实验口径。

### 1.2 目标用户

- 维护论文代码仓库的研究者；
- 第一次参与论文复现的本科生、研究生；
- 需要维护实验规范的学生课题组；
- 审核开源科研贡献的社区维护者。

### 1.3 场景价值

ReproGuard把审查动作前移到PR阶段，使“研究条件是否变化”成为开源协作流程中的显式问题。输出既能作为维护者的核对清单，也能沉淀为JSON/Markdown开放成果，供后续研究者复用。

## 2. 方案定位与创新设计

### 2.1 核心闭环

```text
GitHub PR diff
      ↓
论文 / 实验协议 / 复现档案
      ↓
确定性规则 + 来源受限的模型辅助
      ↓
文件行号 + 论文页码 + 风险说明 + 建议
      ↓
GitHub warning / PR评论 / Job Summary / JSON / Markdown
      ↓
维护者接受、驳回或说明，并更新复现档案
```

### 2.2 与“通用AI代码审查”的区别

本项目不追求覆盖所有bug、性能和代码风格问题，而是专门判断一次变更是否可能改变研究复现条件。差异不只是换提示词，而是引入以下自主设计：

1. 论文/协议约束与PR参数新旧值对齐；
2. 面向科研流程的参数词表和结构化风险类别；
3. diff来源`D###`、论文来源`P###`的引用白名单；
4. 模型与确定性规则的权限隔离；
5. `needs_human_review`人工复核状态；
6. 从真实漏报反推规则完整性条件的评测闭环。

### 2.3 跨学科扩展方式

系统核心输入不是“必须存在可运行代码的论文”，而是Git可见的数字材料。当前参数规范已覆盖机器学习的学习率、批大小和评价指标，也能表示生物信息学的参考基因组、实验协议中的温度、浓度、时长和阈值，以及社会科学中的清洗和排除规则。

系统只证明“提交材料发生了什么变化”，不证明线下实验真实发生，也不代替领域专家判断。第一版用代码复现作为成熟主线，跨学科协议作为结构扩展能力。

## 3. 系统设计与实现

### 3.1 架构

系统由六部分组成：

1. 输入层：PR unified diff、PDF/TXT/Markdown论文或协议、本地仓库；
2. 证据解析层：diff文件与行号解析、PDF逐页文本提取、仓库文件扫描；
3. 规则层：参数变化、种子删除、依赖变化、数据/评价流程变化等确定性规则；
4. 模型辅助层：Ollama或OpenAI兼容接口，做科研语义补充；
5. 约束层：来源编号白名单、结构校验、人工复核标记；
6. 输出层：GitHub注释、单条PR评论、Job Summary、JSON与Markdown报告。

### 3.2 PR差异解析

解析器保留文件路径、hunk、新旧行号以及新增/删除/上下文类型。参数解析支持配置赋值和命令行参数，并把`lr`、`learning-rate`等别名统一为规范字段。

### 3.3 确定性规则

当前PR规则可以识别：

- 学习率、批大小、随机种子、训练轮数、数据集、模型、优化器、损失和评价指标变化；
- 随机种子设置删除；
- 依赖和环境文件变化；
- 数据处理、数据划分、损失函数和评价流程变化；
- 加载器批次数被用作评价结果归一化分母的结构变化；
- 温度、浓度、时长、阈值和参考基因组等协议参数变化。

另保留R001—R015论文—仓库体检规则，用于判断说明文档、依赖、数据获取、实验入口、评价指标和许可披露是否完整。

### 3.4 模型辅助与安全边界

模型获得的是已编号来源，而不是无限制访问项目。输出风险必须引用有效`D###`或`P###`编号；未知编号会被丢弃。模型结果单独保存，不修改规则的状态、严重度、证据或建议。服务不可用时系统返回`unavailable`，规则结果仍可生成。API Key只从环境变量读取。

2026-10-22已通过OpenAI兼容适配器真实调用DeepSeek，实际模型参数为`deepseek-chat`，输入为项目自造的TinyCNN实验文本，抽取状态为`ok`。处理后档案包含2条研究主张、4个复现步骤和4条来源证据；`P002`、`P004`、`P005`、`P007`均通过逐行核对，未发现虚构编号或无来源数值。模型同时指出8类缺失信息。团队未修改生成文件，另建逐项复核记录；沈智和已签名确认接受两条主张和四个步骤，同时保留全部缺失提醒。生成文件中的`needs_review`和`pending`原始状态不作事后修改。当前输出未保存原始HTTP响应或服务端具体版本，因此不将处理后档案表述为逐字原始输出。

### 3.5 GitHub Action

复合Action负责获取真实PR diff、调用审查引擎、输出warning和Job Summary，并用隐藏标记创建或更新同一条PR评论，避免重复刷屏。规则模式不需要模型或密钥。计划公开引用为`hm10629/reproguard@v1`。

`【必须人工补充】`：远程仓库、`v1`标签和跨仓库在线运行尚未完成，发布后填写运行URL和截图。

## 4. AI与开源融合

### 4.1 AI的必要作用

规则适合检测明确的参数和结构变化，但不同学科会用不同名称表达同一研究概念。模型层用于非结构化实验步骤抽取、同义概念归一和难以枚举的科研语义提示。系统没有把AI当作最终裁判，而是通过来源限制和人工复核使其成为可审计助手。

### 4.2 开源资源的关键作用

- Python标准库支撑核心应用、测试和网络适配；
- BSD-3-Clause许可的pypdf用于逐页解析论文PDF；
- GitHub Actions和REST API提供开源协作载体；
- Ollama和开放模型提供可选的本地推理路径；
- 公开论文、开源仓库和真实历史PR构成可核验案例。

完整版本、来源、许可义务和自研边界见《开源及第三方资源使用清单》。第三方论文PDF、代码快照和完整上游diff均不随本项目重新分发。

## 5. 真实案例与可验证效果

### 5.1 Pytorch-UNet PR #141

案例来源为`milesial/Pytorch-UNet`已合并PR #141，合并提交为`32ee0fe…`，真实diff SHA-256为`4dfe9e…`。系统当前输出3项高风险人工复核点：

1. `eval.py:12/32`：评价结果的归一化分母改为数据加载批次数；
2. `eval.py:25/27/29`：Sigmoid、Dice和交叉熵相关评价流程发生变化；
3. `train.py:38`：`drop_last=True`改变参与验证的样本范围。

该案例展示了诚实的规则演进：旧规则0条风险；扩展管线词后2条；人工复核发现1处评价分母漏报；加入结构规则后报告3条。系统不声称上游修改错误，只要求维护者核对论文、测试和结果是否同步。

### 5.2 U-Net核心规则人工评测

团队对固定commit的`jaxony/unet-pytorch`独立标注R001、R002、R003、R008、R011、R014六条核心规则。基线精确状态一致3/6，缺口召回率50%。失败集中在“出现相关文字，但必要信息链不完整”。完善README完整性、数据获取语境和资源许可边界规则后，同组复测6/6。

必须同时披露：这是同一项目、同一组用于规则改进的样本，而且六条全为缺口正类；6/6不代表整体准确率100%，不能评估误报率或跨项目泛化能力。

### 5.3 工程验证

- 自动化测试：152项，全部通过；
- 真实8页U-Net PDF可由pypdf解析；
- 机器可读和人类可读评测报告均可重复生成；
- 第三方原件、密钥和含本机路径的旧报告由`.gitignore`排除。

## 7. 局限性与后续计划

1. 当前真实人工评测样本较小，且无正常负类；
2. 规则在同组样本上改进，需要未见项目外部验证；
3. 已完成一次自造公开样例上的真实模型调用，但样本规模小，且未保存原始HTTP响应，不能据此声称普遍模型效果；
4. Action尚未在远程公开仓库完成跨仓库验收；
5. 跨学科支持目前是参数Schema和数字材料审查，不等于自动理解所有领域实验；
6. 系统不运行任意第三方论文代码，也不证明论文结论正确。

25日前优先完成GitHub发布与在线Action验证、演示截图以及报告/PPT/视频定稿；多项目大规模评测作为后续开放计划。
