# 科研复现体检员：项目方案书

## 1. 项目定位

科研复现体检员是一款面向科研新手、学生课题组和开源论文复现者的辅助工具。它不把目标设为“和论文聊天”，而是把论文中的实验要求与代码仓库中的实际材料进行对照，找出复现前必须补齐的信息。

核心问题：

> 这项实验目前是否具备复现条件？如果不具备，缺什么，证据在哪里，下一步谁来补？

## 2. 用户与场景

### 目标用户

- 第一次复现论文的本科生或研究生
- 需要整理实验规范的课题组
- 维护论文代码仓库的研究者
- 想快速评估开源项目可复现性的学习者

### 典型场景

用户准备复现一篇机器学习论文，手中有论文 PDF 和作者公开的代码仓库，但不确定：

- 使用了哪个版本的数据集
- 训练集、验证集和测试集如何划分
- 依赖和硬件环境是什么
- 是否固定了随机种子
- 哪条命令可以启动实验
- 论文表格中的结果是否能由代码生成

系统需要把这些疑问整理成证据化的检查结果。

## 3. MVP 范围

### 输入

- 论文 PDF
- Git 仓库 URL，或本地代码目录
- 可选：实验配置文件、运行日志、结果表格

### 输出

- 实验要素清单
- 论文与代码的对应关系
- 复现风险检查表
- 高、中、低三级风险
- 每项风险的证据位置
- 可执行修复任务
- Markdown 和 JSON 两种报告格式

### 不在 MVP 范围

- 自动购买或分配 GPU
- 自动修改第三方仓库并提交代码
- 证明论文结论真实有效
- 覆盖所有科研领域
- 一开始支持多用户复杂协作

第一版优先支持机器学习论文，因为其数据集、模型、训练参数和评价指标相对容易结构化。

## 4. 用户流程

1. 创建一次“复现检查任务”。
2. 上传论文并输入代码仓库。
3. 系统解析论文实验部分和仓库结构。
4. 用户确认系统抽取的实验要素。
5. 系统按规则逐项检查。
6. 用户查看风险、证据和建议。
7. 用户将风险导出为 Issue 或待办事项。
8. 用户补充材料后重新检查。

其中第 4 步必须保留人工确认，以降低模型误读论文的影响。

## 5. 检查结果模型

每一项检查至少包含：

```json
{
  "rule_id": "R005",
  "title": "是否说明随机种子",
  "status": "missing",
  "severity": "medium",
  "finding": "未在论文和仓库中找到明确的随机种子设置",
  "evidence": [
    {
      "source": "repository",
      "location": "train.py:42",
      "quote": "..."
    }
  ],
  "suggestion": "在训练入口增加固定随机种子，并在 README 中说明",
  "confidence": 0.86
}
```

状态建议使用：

- `found`：已找到明确证据
- `partial`：找到部分信息，但不足以复现
- `missing`：未找到必要信息
- `not_applicable`：该检查项不适用
- `needs_review`：需要人工确认

## 6. 技术路线

### 文档与代码处理

- PDF：pypdf（BSD-3-Clause）
- 文本切分：按页码、章节和段落保留来源位置
- 代码：文件树扫描、Python AST、配置文件解析
- 仓库：Git 命令或 GitPython，保留提交版本

### 智能分析

当前实现分成两层，规则层始终是权威：

- **规则引擎（默认、离线）**：负责 R001-R015 的全部判定、严重度和证据，任何模式下都不改变。
- **模型辅助层（可选、本地）**：通过本机 Ollama 的开放模型做实验要素抽取、同义概念归一和人工复核提示，结果放在报告的 `model_assistance` 区块。

约束：

- 模型只能引用工具给定的来源编号（论文行 `P###`、仓库行 `F###`），未知编号一律丢弃，不会进入结果。
- 模型不得写入或改写 Finding 的状态、严重度、结论、建议和证据。
- 模型不可用时报告标注 `unavailable` 并给出本地配置提示，规则结果不受影响。
- 适配层只用标准库，不新增第三方 Python 依赖。

Pydantic 或同类结构化模型约束、本地向量检索仍属后续增强，不作为当前阶段依赖。

### 应用形态

**当前已实现**（基于 Python 标准库，无第三方 Web 依赖）：

- 命令行入口：`src/cli.py`
- 本地网页：`src/web.py`，使用标准库 `http.server`，默认监听 `127.0.0.1:8765`
- 报告：JSON 与 Markdown 两种格式，另有网页视图
- 无数据库，无 Docker 依赖，获取代码后可直接在本机运行

**后续扩展**（尚未实现，不作为当前阶段依赖）：

- 后端：FastAPI
- 前端：React 或 Vue
- 首版数据库：SQLite
- 部署：Docker

### 模型调用层的适配器

当前实现支持两类适配器：

- `OllamaClient`：本地优先，适合比赛演示和未公开材料；
- `OpenAICompatibleClient`：可接入 DeepSeek，也可配置为 vLLM、LM Studio 或其他兼容服务。

两类适配器共用来源编号白名单、结构校验和人工复核流程。API Key 只从环境变量读取，不写入仓库或报告。`【必须人工决定】` 云端服务是否可以接触当前科研材料，并人工核对模型版本、许可证/服务条款和数据保留政策。

## 7. 评测方案

先建立一个小型人工标注集，而不是直接用模型自评：

- 选择 10 个具有公开代码的开放机器学习论文项目
- 每个项目人工标注 10 个检查项
- 记录“论文明确说明”“仓库明确说明”“两边都没有”“需要人工判断”
- 测试系统是否识别出缺失项，并检查证据定位是否正确

**当前状态（截至 2026-10-22）：已完成一个真实公开项目的6条核心规则人工标注与正式评测；多项目评测仍属于后续扩展。**

- `data/` 目录下目前只有一个自造固定样例 `data/examples/incomplete-ml-project/`，含 R001-R015 共 15 条人工预期值，用途是验证规则本身，**不是真实论文评测集**。
- 评测骨架已经建立并可运行：`data/evaluation/`（格式说明与 schema）、`src/evaluation.py`（评测脚本）、`tests/test_evaluation.py`（单元测试）。U-Net第三方PyTorch实现已完成人工确认的6条核心规则标注；初始基线3/6一致，针对已知失败模式改进后同组复测6/6。该结果不代表跨项目准确率。
- 真实项目需要由人选择合法来源并提供数据，不得由工具自动下载或虚构。

第一版目标（**均为目标值，尚未实测**）：

- 结构化实验要素抽取准确率达到可人工修订的水平
- 高风险检查项不允许无证据输出
- 报告中的证据覆盖率达到 90% 以上
- 用户可以在 5 分钟内理解一份报告并开始修复

这里的目标用于指导原型迭代，不代表产品效果承诺。注意「证据覆盖率」在 `src/analyzer.py` 中的分母排除了 `missing` 项，因此该指标不衡量漏报，单独使用不足以说明有效性。

## 9. 差异化

项目不以“更会聊天”为主要卖点，而以以下能力形成差异：

- 论文、代码、配置和结果之间的证据关系
- 面向复现工作的检查规则
- 从风险发现到修复任务的闭环
- 可重复运行的检查结果
- 支持本地部署和科研资料保护

## 10. 风险与应对

### 模型幻觉

应对：所有结论必须绑定证据；找不到证据时输出“未找到”，不猜测。

### 论文结构差异大

应对：先支持机器学习论文，逐步增加领域模板。

### 代码仓库无法直接运行

应对：MVP 先检查复现条件，不把“成功运行”作为唯一判定。

### 报告过于复杂

应对：首页只显示高风险项和下一步动作，细节放入证据面板。
